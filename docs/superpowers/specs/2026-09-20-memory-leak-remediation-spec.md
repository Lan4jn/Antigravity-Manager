# 内存修复补全规格

日期：2026-09-20。适用基线：`fix/memory-leaks@f33b1bdf4980e4f7b94db8322dcfa75152a75c52`。

关联：[检查报告](../reviews/2026-09-20-memory-leak-review.md)、[开发计划](../plans/2026-09-20-memory-leak-remediation-plan.md)。

## 1. 开发目标

在现有分支上完成以下可验证结果：

1. 内存日志正文的**实际保留分配**受预览上限约束，完整数据库正文保持不变。
2. 同进程再次初始化代理池后，配置共享和热更新继续正确，初始化完成即可使用最新配置。
3. SignatureCache 的四层和 CacheManager 的三层按最近成功访问顺序淘汰，TTL 语义保持独立。
4. 一个持续活跃的会话不能无限积累签名历史；历史数量与签名分配有明确上限。
5. 回归测试直接覆盖以上不变量，整体失败与基线对照后能够归因。

这是四项定向修复，不代表任意负载下进程 RSS 有固定上限。HTTP 并发正文、数据库写入积压、其他缓存的大条目及分配器保留页不属于本轮上限承诺。

## 2. 方案与边界

沿用现有 Mutex、DashMap、Arc、Tokio 和缓存接口，在所属模块内补充字段及局部帮助函数。配置以 manager 持有的 Arc 为规范来源；缓存把过期时间和访问时间分开。新增预算采用代码常量，无需新增用户配置或依赖。

保持当前默认值：100 条日志、16 KiB 正文前缀、现有截断标识、各缓存外层容量和 TTL、WebSocket 与 Vision 的现有条数限制。

### G1：日志分配约束

- 一个正文的 UTF-8 前缀最多 16,384 字节；超长时在完整字符边界截断，再追加现有标识。
- 通过前缀直接构造新的 String；内存摘要构造期间不得先 clone 完整正文再截断。
- 所有正文，包括 `len` 很小但原 `capacity` 很大的 String，都重新按实际预览大小构造。
- 标准 Rust String/Vec 分配语义下，摘要正文 capacity 应不超过 `16_384 + suffix.len()`；短正文不会带入输入的空闲容量。
- 100 条日志的两个正文容量总和不超过 `100 * 2 * (16_384 + suffix.len())`。其他元数据单独计入，不把该公式描述为整个队列或整个进程的内存上限。
- `None`、空字符串、多字节文本、边界长度均保持合法语义。
- 原始 log 的正文不被修改，数据库读取仍得到完整请求体/响应体。

### G2：代理池共享配置

- `init_global_proxy_pool` 改为可等待的初始化流程。返回时，新配置和账号绑定同步已完成，不依赖 sleep 等待后台复制。
- 全局 manager 继续复用。AxumServer 与 AppState 的 `proxy_pool_state` 均从该 manager 获取同一规范 Arc。
- `Arc::ptr_eq(server_state, manager_config)` 是生命周期内必须成立的不变量。
- 再次初始化后修改代理池开关、代理列表、绑定、检查间隔，manager 与服务观察到相同值。
- 同一规范 Arc 再次传入初始化不会发生读写锁自锁；先释放读 guard，再获取写锁。
- 并发初始化返回同一 manager。并发提交完整配置的先后可由锁获取顺序决定，但完成后配置与绑定必须对应同一次更新；必要时用 manager 内的更新锁串行化“替换配置并同步绑定”。
- 热更新通过同一更新入口同步配置、绑定，再按原有行为清理 HTTP client cache。
- 普通逻辑启停仍保留 Admin Server。验证重复启动健康检查最多一个活动任务；本轮不把代理逻辑停用改成管理服务器销毁。

### G3：真正的最近访问淘汰

覆盖 SignatureCache：工具签名、签名家族、会话签名、会话 reasoning；覆盖 CacheManager：SI、tools、prefix。

- 为条目增加 `last_accessed: Instant`（或等价单调访问序号）。创建和有效写入更新它。
- 仅成功返回有效缓存值的 getter/lookup 刷新访问时间；过期或指定历史轮次不存在的 miss 不刷新。
- prefix 的有效 `record_implicit_hit` / `record_explicit_hit` 也视为访问；过期条目不因计数而复活。
- 淘汰先删除过期项，再淘汰 `last_accessed` 最小项。相同时可按 key 确定顺序。
- `timestamp`、`created_at`、`expires_at` 继续承担原 TTL/创建时间职责。读取不得延长 TTL；原有写入刷新 TTL 行为保留。
- SignatureCache 在一次操作返回后保持容量上限。DashMap 并发写入可在操作执行中短暂超限，所有写入结束后必须收敛到上限。
- DashMap 的 entry guard/迭代器必须在 remove、retain 或其他可能取得相同 shard 写锁前释放；不跨 await 持有 guard。
- 保留现有缓存统计含义和 API 返回类型。

### G4：会话签名历史预算

以下是本轮选定的工程预算，不是对旧行为的描述：

```rust
const SESSION_SIGNATURE_HISTORY_LIMIT: usize = 256;
const SESSION_SIGNATURE_HISTORY_BYTES: usize = 1024 * 1024;
```

- 每个 session 最多 256 条 message_count 历史。
- 每个 session 保留签名的 `String::capacity()` 总和不超过 1 MiB。插入时以实际签名内容构造紧凑 String，避免接收带大额空闲容量的输入分配。
- 每次有效写入后，若超条数或字节预算，按 message_count 从小到大删除，优先保留最近轮次。
- 单条签名长度大于 1 MiB 时不缓存该输入；不截断签名、不返回损坏签名。已有合法缓存维持原样。
- 小于现有最短签名长度的输入继续被忽略。
- 合法输入触发 rewind 时，删除高于当前 message_count 的未来历史，再执行现有同轮“仅更长签名覆盖”规则和预算淘汰。
- 同轮短签名不替换长签名；更新后字节预算使用实际保留值计算。
- 写入已过期的会话时先重建空历史，避免刷新 timestamp 使过期历史复活。
- 被淘汰轮次返回 None；latest getter 返回仍保留历史中最大 message_count 的签名。
- 消费端继续使用现有缓存缺失路径，不为补偿淘汰而伪造签名或绕过上游校验。

预算约束签名历史条数和签名字符串容量；会话 key、HashMap 元数据及其他层单条内容有各自成本。该预算不是全局 1 MiB 承诺。

## 3. 验收矩阵

| 编号 | 必须通过的验收 |
|---|---|
| A1 | 10 MiB 正文得到合法预览，capacity 达到 G1 上限；原正文不变。 |
| A2 | 中文/emoji 边界、空/None、恰好上限、短文本大 capacity；100 条循环替换后的正文容量总和有界。 |
| A3 | 数据库写入和读回完整正文，测试使用隔离数据目录和唯一 ID，等待持久化完成。 |
| A4 | 两次初始化后 Arc 相同，返回时配置/绑定已同步；热更新各字段立即被 manager 观察。 |
| A5 | 首次创建后的重试路径、传入同一 Arc、并发初始化、重复启动健康检查无死锁/重复任务。 |
| A6 | 七层缓存分别覆盖“旧 hot 被读取，cold 未读取，再插入超限”：hot 保留，cold 淘汰。 |
| A7 | 命中不延长 TTL；过期项及历史轮次 miss 不更新访问状态；统计及容量保持正确。 |
| A8 | 单会话连续 10,000 轮写入后最多 256 条；最新值可取，最旧值缺失；字节总和不超过预算。 |
| A9 | 大签名触发字节淘汰；超预算单条拒绝；同轮覆盖、rewind、过期会话重建均符合 G4。 |
| A10 | 多会话外层上限、DashMap 并发写入后的容量收敛、任务退出及原有关联测试通过。 |
| A11 | cargo check 与定向测试通过；整体测试失败完成同环境基线归因，修复新增失败。 |

## 4. 测试与交付约束

测试放在现有模块中。通过私有字段注入时间或内部可测试函数构造边界，不用长时间 sleep 证明 TTL 或 LRU。任务完成使用 handle、通知或有超时的条件等待。

数据库测试在独立进程及临时 `ABV_DATA_DIR` 下运行；注意已有测试会修改进程环境，串行或隔离运行，避免共享全局状态造成假失败。基线与候选使用相同命令、环境、线程策略及可比依赖锁文件。

完成后交付代码、回归测试、检查结果文档。结果须列出 A1–A11 对应证据、命令退出码和遗留限制；所有基线失败都要标明归因状态。不得以“新增测试通过”替代整体验证结论。
